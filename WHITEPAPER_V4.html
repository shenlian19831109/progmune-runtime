1. 问题声明：从 V2.5 到 V4 的跨越

V2.5 的核心突破是知识回路闭环——抗体从 Failure Corpus 自动生成，通过 L1/L2/L3 三层回流到规划器。但这一闭环存在根本局限：

V2.5 局限V4 解决方案
抗体只能匹配已有错误模式Frontier BFS + Goal Templates 可发现新路径
无法量化"哪个策略更好"LearningRanker + Pairwise Preference
不知道系统在哪些协议上薄弱Coverage Engine + Difficulty Map
协议知识靠手工编写Transition Synthesizer + Knowledge Governance
优化方向靠猜测Error Budget Dashboard + Off-Policy Replay
V4 核心命题：AI 生成的代码在进入代码库之前，必须先通过一个免疫层——不仅可验证、具备记忆，还能通过反馈数据持续进化、主动发现知识缺口、并自动补全协议规则。

关键设计原则：策略只产生候选，不打分。评分是 Ranker 的职责。这确保未来增加新策略或替换排序器时，不需要修改任何策略代码。

3.2 三个搜索策略

策略知识源优势劣势
CorpusStrategy Failure Corpus 历史轨迹 真实修复经验，置信度高；冷启动友好（有数据时） 依赖历史数据，新错误类型无法匹配
ProtocolStrategy SSG 协议图 BFS 无需历史数据，纯推理；资源清理总是能被发现；P3.14 Frontier 替代模板依赖 受协议规则数量限制；规则中没有的函数永远找不到
AntibodyStrategy 抗体注册表 高置信度（ACL-3+ 抗体经过充分验证）；快速通道 依赖先前失败积累；新违规类型初期无抗体

3.3 跨源证据合并

同一修复路径可能同时来自多个策略。合并后 evidenceSources: ["corpus", "protocol", "antibody"]，可信度显著提高。

3.4 排序器：七维特征向量

特征含义范围
protocolSafety路径满足安全约束的程度0-1
historicalSuccessRateCorpus 历史成功率0-1
actionCount修复路径中的动作数整数
latencyCost延迟成本（逆）0-1
auditability可审计性（短路径更高）0-1
corpusEvidence语料库证据数量整数
source来源策略枚举

四种排序模式：rankSafety()（金融系统）、rankPerformance()（实时系统）、rankAuditability()（合规团队）、rankOverall()（默认加权组合）。

默认权重：score = 0.4×safety + 0.3×successRate + 0.2×performance + 0.1×auditability

4. P2.5-2.6：可学习系统的数据基础

4.1 Telemetry Layer

组件功能复杂度

RepairLifecycleproposedAt → acceptedAt → executedAt → executionSucceeded 完整链RLHF 格式

4.2 LearningRanker

核心创新：系统能根据真实反馈数据调整排序。

effectiveReward = 0.5 × acceptanceRate + 0.5 × executionSuccessRate
adjustedScore = baseScore × 0.7 + effectiveReward × 0.3
关键设计：accepted ≠ good。用户可能大量接受快速但泄漏资源的修复。系统通过学习 acceptance + execution success 的组合信号来避免"学坏"。

4.3 已证明的自进化回路

Ranking Evolution Test：Phase 1: A (safe) 接受 90 次 → A 排第一。Phase 2: B (fast) 连续接受 100 次且执行成功 → B 反超 A。

4.4 Off-Policy Replay

Δ:                          +66.7%  ✅

反馈数据中存在可学习的信号。闭环已被证明有效。

7. P3.10-3.15：候选发现增强

7.1 Goal-conditioned Planner

22 个 Goal Template 将自然语言目标展开为前置条件链：

"logout user" → [verify_password, generate_jwt, create_session]
"authenticate" → [verify_password, generate_jwt, create_session]
"safely write file" → [open_file, write_file]

效果：insufficient_history 从 39% → 14%。局限：模板覆盖率受手动维护限制。

7.2 Frontier Explorer（不依赖模板的 BFS 搜索）

searchFrontier(rules, ["UNAUTHENTICATED"], ["SESSION_ACTIVE"])
  → { actions: ["verify_password","generate_jwt","create_session"], cost: 3 }

searchFrontier(rules, ["FILE_OPEN"], [])
  → { actions: ["close_file"], cost: 1 }

效果：bad_protocol_model 从 6% 永久归零。

7.3 Cross-Protocol Planner

协议间桥接：AuthProtocol → FileProtocol (SESSION_ACTIVE → INIT)，支持跨协议修复链。

7.4 Search Trace

结论

Progmune Runtime V4 完成了从"规则验证器"到"可学习系统"的进化。四个飞轮已形成闭环，系统具备从反馈中学习、主动发现知识缺口、自动补全协议规则、并安全验证新知识的能力。

A. 协议图

AuthProtocol:
  UNAUTHENTICATED → verify_password → PASSWORD_VERIFIED
  PASSWORD_VERIFIED → generate_jwt → TOKEN_ISSUED (inv: PASSWORD_VERIFIED)
  TOKEN_ISSUED → create_session → SESSION_ACTIVE (inv: TOKEN_ISSUED)
  SESSION_ACTIVE → logout → UNAUTHENTICATED (inv: SESSION_ACTIVE)
  TOKEN_ISSUED → revoke_token → UNAUTHENTICATED (inv: TOKEN_ISSUED)

FileProtocol:
  INIT → open_file → FILE_OPEN
  FILE_OPEN → read_file / write_file → FILE_OPEN
  FILE_OPEN → close_file → ∅ (inv: FILE_OPEN)

DBProtocol:
  INIT → connect_db → DB_CONNECTED
  DB_CONNECTED → query_db → DB_CONNECTED
  DB_CONNECTED → disconnect_db → ∅ (inv: DB_CONNECTED)

IRProtocol:
  IR_STALE → extractIR → IR_EXTRACTED (inv: IR_STALE)
  IR_EXTRACTED → validateAction → ACTION_VALIDATED
  ACTION_VALIDATED → validateActionSequence → SEQUENCE_VALIDATED (inv: ACTION_VALIDATED)
  SEQUENCE_VALIDATED → emitCode → CODE_EMITTED (inv: SEQUENCE_VALIDATED)
  CODE_EMITTED → recordSession → SESSION_RECORDED (inv: CODE_EMITTED)

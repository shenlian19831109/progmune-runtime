摘要

程序验证——特别是 AI 生成代码的协议合规性验证——目前处于工程化阶段：规则由经验编写，性能由 Benchmark 驱动迭代，优化方向依赖试错。本文提出，程序验证需要建立自己的科学基础：一套可以定量预测系统行为、识别能力边界、并指导资源分配的理论框架。

基于 Progmune 在 7 个开源代码库、2,567 条执行轨迹、81 个协议转换空间上的实验数据，我们提出两个实证规律（empirical regularities）——注意这仍是基于有限数据的初步发现，需要更多实验验证和独立复现才能确立为"定律"：

实证规律 1 · 两因子模型
协议验证覆盖率 = f(规则词汇, 轨迹密度)。单一因子无法独立将覆盖率推至阈值以上。
实证规律 2 · 覆盖率-召回率对应
Recall 的理论上限 ≈ 协议空间覆盖率。F1 = harmonic_mean(Coverage, Precision)。

实验表明，18 条定向注入词汇的合成轨迹实现了 2,567 条同类轨迹无法达成的覆盖率提升（+28.4%）。这证明了当前瓶颈不是"数据不够"，而是"词汇缺失"——一个无法通过工程迭代解决的结构性问题。

1. 问题：程序验证的"工程化陷阱"

1.1 现状

当前程序验证系统——无论是静态分析工具（CodeQL、Semgrep）还是 AI 驱动的验证运行时（Progmune）——共享一个工作模式：

添加规则 → 跑 Benchmark → 看 F1 → 调整或回滚 → 重复

这个模式的本质是经验驱动的工程迭代。它在早期有效——当规则从 0 到 10 条时，每次迭代都带来显著的 F1 增益。但当规则积累到一定数量后，系统陷入困境：

现象Progmune 数据根本原因
F1 停滞v6→v7: F1 23.3% → 23.0%（下降）调参无法突破词汇天花板
轨迹无效723→2,567 条轨迹，覆盖率 0% 增长同类轨迹不增加新词汇
瓶颈误判以为需要更多轨迹，实际需要新规则缺乏覆盖率-召回率理论

1.2 工程化的三个症状

症状一：无法预测规则增益。 当一条新规则被添加时，它对 F1 的贡献是未知的——只能"加了再测"。资源被浪费在低 ROI 的规则上。

症状二：无法量化能力边界。 Progmune 有 109 条规则、71 个状态、21 个命名空间。但它覆盖了多少协议行为空间？在 curl 上的 23.4% 精确率是因为"规则太宽泛"还是"规则根本没触及正确的协议状态"？工程化方法无法区分。

症状三：优化方向由直觉驱动。 "我们下个 quarter 加 10 条规则。"为什么是 10 条？为什么是这些规则？工程化方法无法回答。

1.3 从工程化到科学化

科学化的核心转变是：从"做了再测"到"预测再验证"。

维度工程化科学化
规则操作加规则 → 测 F1 → 回滚预测规则对覆盖率的贡献 → 加规则 → 验证预测
覆盖度"我们有 68 条规则""68 条规则覆盖了 TLS 状态空间的 56%，置信度 ±8%"
瓶颈诊断"F1 太低，需要更多数据""Recall=50% 受限于词汇覆盖率 39.5%，需在 tls/auth/dev_pipeline 注入 13 个转换"
知识增长按季度计划加规则按缺口地图的 ROI 排序加规则

2. 两个实证规律

2.1 实证规律 1：两因子覆盖率模型

实证规律 1 · Two-Factor Coverage Model
Coverage(ns) = Vocabulary(ns) × Density(ns)

其中:
  Vocabulary(ns) ∈ {0, 1}  — 该命名空间的规则是否出现在任何轨迹中
  Density(ns) ∈ [0, 1]     — 在词汇存在的前提下，轨迹覆盖的转换比例
  Coverage(ns) ∈ [0, 1]    — 该命名空间的实际验证覆盖率
  • Vocabulary = 0 → Coverage = 0，无论有多少轨迹。这是硬天花板。
  • Vocabulary = 1 → Coverage = Density，且 Density 在 ~5 条轨迹/转换后饱和。
  • 两个因子是乘法关系，不是加法关系。任一因子为 0，整体为 0。

实证（E2 实验）：

条件轨迹数覆盖率说明
仅生产 Corpus2,56739.5%Vocabulary 覆盖 7/18 命名空间
+18 条合成轨迹2,58567.9%Vocabulary 扩展到 13/18 命名空间
边际增益+18+28.4%18 条词汇注入 > 2,567 条同类轨迹
覆盖率饱和曲线： 39.5% ───────────────────── (723 条轨迹后完全饱和, 0% 增长) ↑ │ 瓶颈: Vocabulary │ 67.9% ───────── (+18 条词汇注入, +28.4%)
推论 1.1 · 级联效应
为一个命名空间注入轨迹，可能激活相邻命名空间的规则词汇。E2 实验中，auth + payment 的注入级联激活了 registration（4 转换）和 printlab_order（2 转换）。这是因为协议命名空间之间存在共享词汇。
推论 1.2 · 饱和度
Density 因子的饱和速度远快于直觉。在 Progmune 的 81 个协议转换空间中，约 180 条轨迹后 Density 即饱和。99% 的轨迹收集预算应该分配给词汇扩展，而非密度提升。

2.2 实证规律 2：覆盖率-召回率对应

实证规律 2 · Coverage–Recall Correspondence
Recall_ceiling(project) ≈ WeightedCoverage(project)

其中:
  WeightedCoverage(project) = Σ usage_weight(project, ns) × Coverage(ns)
  F1(project) ≈ harmonic_mean(WeightedCoverage(project), Precision(project))
  • 协议验证的召回率上限由协议空间的词汇覆盖率决定。
  • 精确率由规则质量和 FP 抑制机制决定——独立于覆盖率。
  • F1 是两个维度的调和平均——较低的那个主导。

实证（E3 实验 + C benchmark）：

项目WtCovRecallPrecisionF1主导瓶颈
curl59.3%75.0%23.4%35.6%Precision（FP 过多）
libssh63.9%85.7%27.3%41.4%Precision（FP 过多）
C benchmark39.5%50.0%15.2%23.3%Coverage（词汇不足）

覆盖率→召回率的方向性一致，但 n=2 时两点总能在平面上确定一条直线，任何相关性度量在此样本量下都不具备统计意义。完整的验证需要 n≥4（需补齐 nginx 和 redis 的 Benchmark 数据）。

推论 2.1 · 瓶颈诊断法则
若 Recall < Coverage    → 瓶颈在规则精度（规则太宽泛，漏判）
若 Recall ≈ Coverage    → 瓶颈在词汇覆盖（需要新命名空间的规则）
若 Precision < 30%      → 瓶颈在 FP 抑制（需要 VI 或规则收紧）
推论 2.2 · F1 提升预测
ΔRecall ≈ ΔCoverage × (1 - current_recall / current_coverage)
ΔF1 ≈ harmonic_mean(current_recall + ΔRecall, current_precision) - current_F1

C benchmark 预测（注入 tls + dev_pipeline + file_upload 词汇）:
  ΔCoverage = +20.9% (17 个新转换 / 81)
  ΔRecall ≈ +10–15%
  ΔF1 ≈ 23.3% → 32–38%

3. 实证基础

3.1 E2：规则词汇注入实验

设计：从协议空间的 81 个有效转换中，选择 3 个零覆盖命名空间（payment 5 + session_mgmt 7 + tls 1）和 1 个部分覆盖命名空间（auth 4），编写 18 条合成轨迹注入到生产 Corpus。

指标结果
覆盖率变化32/81 (39.5%) → 55/81 (67.9%)，+28.4%
级联激活registration（+4）+ printlab_order（+2），超出目标 35%
轨迹效率1.28 转换/轨迹（vs 生产 Corpus 的 0.01 转换/轨迹）
结论
词汇注入是提升覆盖率的高杠杆手段。生产 Corpus 的轨迹效率在 723 条后降至 0——继续收集同类轨迹对覆盖率无贡献。

3.2 E3：覆盖率-召回率相关性

设计：对 curl 和 libssh 两个已测量代码库，基于领域知识标注协议命名空间使用权重，计算加权覆盖率，与 Benchmark 召回率做方向性观察。

方向性观察（n=2，不足以做统计推断）：同一方向上覆盖率更高的 repo 召回率也更高（curl: WtCov=59.3%, Recall=75.0%; libssh: WtCov=63.9%, Recall=85.7%）。但 n=2 时任何两点都确定一条直线——无法排除偶然性。完整验证需要 n≥4。

3.3 C Benchmark 根因分析

问题：Gold Benchmark（4 个 C 开源项目，232 条序列），v6 的 F1 = 23.3%（P=15.2%，R=50.0%）。

  1. Recall=50% 的天花板 = Coverage=39.5% 的直接后果。232 条 C 序列调用了 TLS、认证、授权、会话管理、文件上传等协议——但规则词汇仅覆盖了 39.5%。
  2. Precision=15.2% = 规则爆炸。curl 的 61 条 clean sequences 触发了 452 条 SSG 规则——大部分是过度泛化的误报。
  3. v6→v7 的 F1 下降（23.3%→23.0%）进一步证实：在词汇覆盖不变的前提下，精度调优的边际收益为负。

4. 从工程化到科学化：路径

4.1 科学化的操作性定义

基于 Phase 0 标准，程序验证的"科学化"意味着满足以下五个条件：

#标准当前状态
G1系统行为可被理论预测 两因子模型提供 Recall 预测框架（待 n≥4 验证）
G2规则完备性有量化缺口地图 D2 Gap Map 已完成（8 个命名空间，26 个转换）
G3Confidence 是计算值 D3/D4 公式已定义（待代码实现）
G4知识增长由 ROI 公式驱动 缺口地图提供排序依据（待接入规则开发流程）
G5存在被实验验证的可证伪预测 E2 已验证一项，C benchmark 预测待验证

4.4 局限与下一步验证

本文提出的框架存在以下局限，需要在后续工作中逐一解决：

L1 · 样本量不足（严重程度：高）
E3 的覆盖率-召回率对应分析仅基于 n=2（curl、libssh）。当 n=2 时，两个数据点总能在平面上确定一条直线——任何方向性"一致"都无法排除偶然性。需要补齐 nginx 和 redis 的 Benchmark 测量，使 n≥4，才能进行有意义的统计检验。如果 n=4 时覆盖率与召回率仍保持方向一致，实证规律 2 的可信度将大幅提升；如果方向被推翻，则需要修正理论。
L2 · "实证规律"的措辞（严重程度：中）
本文使用"实证规律"（empirical regularity）而非"定律"（law），以如实反映当前的验证程度。科学史上的定律——如摩尔定律、梅特卡夫定律——通常经过多年的广泛验证和独立复现。两因子模型和覆盖率-召回率对应目前仅基于 Progmune 一个系统的内部实验数据。升级为"定律"需要：（a）独立团队在类似系统上复现；（b）更大样本量（n≥10 repos）；（c）时间维度的验证（模型在新 repo 上的预测能否持续成立）。
L3 · 可证伪预测的验证状态（严重程度：高）
提出的五个可证伪预测中，仅 P3（饱和假说）被 E2 实验验证。P1（C benchmark 词汇注入）和 P2（100% 覆盖率可达成）是框架的关键检验——如果 P1 被推翻（即注入新词汇后 Recall 未提升），两因子模型需要重大修正。P4（nginx 召回率）和 P5（词汇消融实验）是辅助检验。
L4 · 外部有效性（严重程度：中）
两因子模型的验证数据全部来自 Progmune 系统。该模型是否适用于其他程序验证工具（如 CodeQL 的规则覆盖度分析、Semgrep 的模式覆盖度分析）尚不清楚。跨工具的验证将决定这是"Progmune 的工程发现"还是"程序验证的普遍规律"。
L5 · 级联效应的可控性（严重程度：低）
E2 实验中观察到的级联效应（注入 payment 轨迹激活了 registration 转换）暗示协议命名空间之间存在隐式耦合。本文记录了此现象但未建模其机制。如果级联效应在某些场景下产生噪声覆盖，可能降低而非提升验证质量。

5. 总结与展望

5.1 核心论点

程序验证目前处于工程化阶段。它的工作模式（经验驱动的规则迭代）在早期有效，但在面对复杂协议空间时暴露出结构性局限：无法预测规则增益、无法量化能力边界、无法诊断瓶颈根因。

科学化的路径是建立一套可定量预测验证系统行为的理论框架。本文提出的两因子模型和覆盖率-召回率对应规律是这个框架的起点。它们已被 E2 实验（n=2,567+18）和 E3 分析（n=2 repos）初步验证，并产生了五个可证伪的预测——但样本量不足（尤其是 E3 的 n=2）意味着这些仍是"实证发现"而非"确立定律"，需要更多独立验证。

5.3 更广泛的意义

程序验证的科学化不仅仅关乎一个工具的性能提升。如果 AI 生成的代码将成为软件供应链的主要输入，那么验证这些代码的可信度就需要超越"跑一遍测试看看"的工程化思维。我们需要知道——定量地知道——验证系统在哪些协议上可靠、在哪些协议上有盲区、以及需要多少证据才能将置信度从一个水平提升到另一个水平。

这需要科学的程序验证——正如航空工程从试错走向空气动力学，程序验证也需要从 Benchmark 驱动的迭代走向理论指导的预测。

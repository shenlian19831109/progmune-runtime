PROGMUNE · PHASE 0

科学化衡量标准

目标：用 1–2 天明确"科学化"的操作性定义。
没有这个标准，"科学化"会退化为标签，而非实际转变。

1 核心判定标准

维度工程化（当前）科学化（目标）
规则操作 加规则 → 测 F1 → 不好就回滚 预测新规则对 F1 的期望贡献 → 加规则 → 验证预测
覆盖度 "我们有 68 条规则，覆盖了 TLS/SSH/HTTP" "68 条规则覆盖了 TLS 状态空间的 X%，置信度 Y%"
FP 控制 VI 逐条抑制 FP（43% 减少，经验驱动） 给定协议复杂度 N，理论 FP 下界 = f(N)，当前距下界还有 Z%
性能预测 "curl F1=36%，libssh F1=41%——不同 repo 表现不同" "给定 repo 的协议使用特征向量，预测 F1 范围 ±Δ"
知识增长 "下个 quarter 加 10 条规则" "规则完备性缺口 = {具体协议 × 具体状态}，优先级排序由 ROI 公式驱动"

2 各阶段科学化成功标准

Phase 1 状态空间覆盖度

⏱ 2–3 周 📊 输入：Trajectory Corpus + protocols.json

输入：~9 sessions · ~2,558 trajectories · 71 states × 109 rules × 17 namespaces

成功标准（至少达成 2/3）：

  • S1.1 建立 Trajectory→Coverage 数学关系：给定 N 条轨迹，协议覆盖率 C 的置信区间 [C_low, C_high] 可以被计算
  • S1.2 Trust Report 的 Confidence 字段升级为"覆盖度 63% ± 12%（基于 2,558 条轨迹）"
  • S1.3 对 C benchmark（F1=23.3%）给出理论解释：需要 Y 条额外轨迹才能达到 Z% F1
⚠ Red Flag — 伪科学化 Coverage 数字无法追溯到轨迹数据，或者置信区间是固定常数。

Phase 2 验证理论白皮书

⏱ 2–3 周 📄 产出：Science of Program Verification 白皮书
  • S2.1 包含一个可被独立验证的核心定理（不是纯叙述）
  • S2.2 定理的推论可以解释至少一个现有 benchmark 现象
  • S2.3 定理产生一个可证伪的预测，并在 Phase 1 数据上做 back-test
⚠ Red Flag — 伪科学化 白皮书只是重新叙述现有 benchmark 结果，没有可证伪预测。

Phase 3 推理链可解释性

⏱ 2 周 🔗 产出：ViolationTrace 引擎 + Trust Report 升级
  • S3.1 ViolationTrace 在 engine 层是一等类型，包含中间状态的序列化表示
  • S3.2 未读过 protocols.json 的工程师可在 2 分钟内理解违规的因果链
  • S3.3 Trace 长度与理解时间不再是指数关系（推理步数灾难被解决）
⚠ Red Flag — 伪科学化 Trace 只是把已有字段用箭头连起来，工程师仍需查 RFC 才能理解。

Phase 4 飞轮定性建模

⏱ 1 周 🔄 产出：依赖图 + 关键度量定义
  • S4.1 四飞轮依赖关系图（DAG），每条边标注耦合机制
  • S4.2 每个飞轮有 1–3 个可测量关键度量，记录当前基线
  • S4.3 识别至少一个飞轮间的"瓶颈依赖"
⚠ Red Flag — 伪科学化 飞轮图是单向箭头堆砌，没有可测量的度量。

3 全局判定：Progmune 是否已科学化？

Phase 1–4 全部完成后，用以下标准做总体验收：

G1 系统行为可被理论预测

任意新 repo：预测 F1 → 实测 F1，误差在 ±Δ 内

G2 规则完备性有量化缺口地图

缺口 = {协议, 状态, 优先级, 预估 F1 增益} 排序列表

G3 Confidence 是计算值，不是标注

每条 Trust Report 的 Confidence 可追溯到轨迹覆盖度

G4 知识增长由 ROI 公式驱动

规则增长 → F1 增长的预测误差 < 30%

G5 存在至少一个被实验验证的可证伪预测

白皮书中的预测 → 实际测量 → 记录偏差

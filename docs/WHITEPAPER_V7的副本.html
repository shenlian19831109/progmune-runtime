2. 问题与市场 Problem & Market

2.1 核心问题 · The Core Problem

AI 代码生成器（Claude、GPT、Copilot、Cursor）以史无前例的速度产出语法正确的代码。但语法正确 ≠ 安全。

AI code generators produce syntactically correct code at unprecedented speed. But syntax is not safety.

当 AI 生成代码时，它可能：

  • 跳过认证步骤直接访问敏感数据
  • 分配资源后从不释放
  • 关闭连接但未失效会话
  • 提交事务但未检查授权

These are protocol lifecycle violations — invisible to every existing security tool.

2.4 设计哲学：程序免疫学 Design Philosophy: Program Immunology

为什么叫 Progmune？· Why "Progmune"?

Program + Immune = Progmune

程序（Program）+ 免疫（Immune）= 程序免疫系统

Progmune 借鉴生物免疫系统的三层防御结构，构建 AI 生成代码的安全防线。生物免疫系统不依靠"预测病原体长什么样"——它依靠识别"自己"和"非自己"。Progmune 同理：不预测 LLM 会犯什么错，而是从项目中提取程序真相（IR），用它来识别"不符合协议的代码"。

三层免疫防御 · Three-layer Immune Defense

第一层：天然免疫 Innate Immunity

生物类比：皮肤、粘膜——非特异性防御

技术实现：约束引擎 (SVL-1~3)

  • SVL-1: 符号存在性
  • SVL-2: 类型匹配
  • SVL-3: 数据流

Catches hallucinated functions, type errors. Fast, universal.

第二层：获得性免疫 Adaptive Immunity

生物类比：T细胞、B细胞——特异性防御

技术实现：协议安全检测器 (SSG + Protocol State Machine)

  • 语义状态图 (SSG) 强制执行协议步骤
  • 协议状态机检测跨函数生命周期违规

Catches auth bypass, resource leaks. Learned from protocol knowledge.

第三层：免疫记忆 Immune Memory

生物类比：记忆细胞——记录每次感染

技术实现：可审计治理 (Ledger + Certificate + Evolution)

  • 分类账记录完整状态转移链
  • AI 代码证书证明验证通过

Ledger records every transition, certificate proves verification.

Progmune 不信任 LLM 的输出。它从项目中提取"程序真相"（IR）——符号表、类型图、调用图和协议注解——然后用这套真相去约束 LLM 的提议。LLM 被降级为"受约束的提议者"，最终决定权在程序真相。

4.2 Resource Abstraction 资源抽象层 V7 增强

从单词到语义 · From Words to Semantics

create<X> → X 是 MutableResource → 自动需要 Ownership + Validation + Authorization。不依赖实体名的精确匹配——自动泛化到任何实体名。

V4 验证：25/25 核心运行时测试通过。支持 credential / mutable_resource / session / file_asset / reference_data 六种资源分类。动词覆盖包括 hash、generate、encrypt、decrypt。

4.3 Capability Layer Map 能力分层 V7 新增

检测能力的四个层级

层级名称检测能力示例
L1Lexical（词法）Regex trigger + safeguard。调用存在/缺失的二元信号。cleanup vs. no cleanup
L2Control Flow（控制流）函数内调用顺序。A 必须在 B 之前。verifySession 在 addNote 之前
L3Interprocedural（跨函数）跨函数调用图。调用者链是否提供 safeguard。handler → verifySession → addNote
L4Semantic（语义）协议状态机、资源生命周期、类型安全。TLS handshake 顺序

为什么需要能力分层？

V7 的核心发现：不是所有违规都值得用同一种方式解决。在 7 个 C 仓库、27,668 个函数、7,740 个 findings 中：

层级占比可视化策略
L1 (Lexical)82.7% 扩展规则覆盖 — ROI 最高
L3 (Interprocedural)12.4% 有信号，未来可投入
L2 (Control Flow)4.9% 数据不支持当前投入
L4 (Semantic)0.0% 当前规则未设计 L4 检测

这意味着：写规则之前，先问"这个问题属于哪一层？"不要浪费 L1 时间在 L4 问题上。

9. 竞争力与护城河 Competitive Moat

已有的护城河 (V6)

  • 协议知识库：TLS, SSH, HTTP/2, QUIC — 持续演化
  • Resource Abstraction：动词+实体→协议，自动泛化
  • Verification Intelligence：FP 学习循环，自动降噪
  • Governance Pipeline：Verify→Explain→Repair→Certify 完整链路
  • 三层免疫架构：与 CoT 路线的根本差异

V7 新增的护城河

  • 可复现 Benchmark：Gold + Blind + Coverage Dashboard — 每一项能力有数据支撑
  • 实验证据链：7 轮单变量实验 — 每个决策有 Migration Matrix
  • 能力边界量化：L1-L4 分层 — 精确知道当前能解决什么、不能解决什么
  • 规模化统计：7 repos, 27K functions — 统计结论有代表性
  • 研发方法论：Benchmark → Gap → ROI → Experiment → Decision 闭环

最难复制的资产

不是 Detector。不是 Rule。是 Benchmark + Evaluation Framework。

Detector 可以重写。Rule 可以增加。Parser 可以换。但可重复、可量化、可比较的 Benchmark 才是最难建立的壁垒。很多团队一年都搭不出来。

11. 市场策略 Market Strategy

定位：Protocol Compliance Analyzer

不是 "AI Security Scanner" — 而是发现代码是否遵守安全协议。差异化：SAST 找已知模式，Progmune 找缺失的协议步骤。

不卖 "我们什么都能发现"。而是卖："我们擅长发现这些问题，目前不覆盖那些问题"——这反而更容易建立信任。

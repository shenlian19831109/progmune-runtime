第一部分：框架基础

1.1 核心价值：为什么 AI 代码需要"免疫"与"生成"？

在 AI 辅助编程时代，LLM 带来了前所未有的效率，但伴随着三个"认知缺陷"：

🔴 幻觉

LLM 凭空捏造不存在的函数、类或变量，导致运行时错误。例如调用 flushAndClose() 而项目中实际只有 close()。

🟠 类型漂移

参数数量或类型与实际函数签名不匹配。例如给需要 3 个参数的函数只传 2 个参数。

🟡 协议违规

生成违反业务逻辑顺序的代码。例如在用户未认证前就签发 JWT 令牌——不安全的越权操作。

Progmune 将 LLM 从一个"不受约束的代码生成器"降级为"受约束的启发式提议者"，将代码的最终决定权交还给程序真相 (IR)。这意味着系统不仅能消除代码幻觉、保障协议安全，还能通过学习历史错误"越用越聪明"。

1.2 核心哲学：以免疫保障生成，以生成驱动免疫

🛡️ 免疫 → 生成

通过多层验证机制，确保 AI 生成的每一步都符合程序真相和业务逻辑。只有在免疫系统确认安全后，代码才能被发射执行。

类比：生物免疫系统在允许物质进入血液前先检查其安全性。

🚀 生成 → 免疫

每次生成失败都是一次"感染事件"。系统从中学习，形成抗体规则和免疫记忆，使未来的生成更精准、更安全。

类比：感染后，免疫系统产生记忆细胞，对同类病原体产生更快更强的反应。

对开发者的直接价值：
  • 🚫 终结代码幻觉：100% 保证只调用项目中真实存在的函数和变量
  • 🛡️ 协议级安全：自动拦截非法的业务逻辑跳转
  • 🧠 越用越聪明：从失败中学习，自动形成"抗体"，减少 LLM token 消耗
  • 🚀 提升开发效率：减少调试和重构 AI 生成代码的时间

1.4 LLM+Graph 联合架构 — 为什么是"联合"而非"替代"？

经过 25+ 次对照实验，跨 14/56/132/186/519 五种函数规模，验证了一个关键假设：LLM 和 Graph 各有不可替代的优势，正确的分工是"LLM 跨语义鸿沟选种子 + Graph 做数据流路由连成链"。

方法逻辑519 函数精度
关键词匹配intent.split() → fn.includes(kw)89%
纯 Capability Graph关键词种子 → Beam Search76%
LLM + Graph ✅LLM 语义选种子 → Graph 数据流路由92%
架构验证结论：LLM 擅长理解自然语言意图（跨语义鸿沟），但不擅长精确匹配项目内的函数关系。Graph 擅长精确的函数间数据流路由，但无法理解模糊的自然语言。两者互补——分工而非替代——是正确架构。

2.2 框架组成逻辑 — 每个部分为何存在

Progmune 的架构由 9 个核心组件组成，每个组件解决一个特定的问题。理解它们之间的因果关系，就能理解整个框架的设计逻辑：

#组件为什么需要它？它做什么？
1 LLM Proposer 自然语言意图无法直接转化为代码。需要 LLM 的语义理解能力来"翻译"意图。 将用户意图转化为抽象动作序列提议（如"打开文件→写入→关闭"）。不再直接生成代码——这消除了 LLM 随意发明语法的可能。
2 Strategy Planner + Semantic Topology LLM 的提议可能使用模糊的函数描述（"写文件"），而不是项目中的确切函数名（writeConfigFile）。需要一个"翻译层"。 从 IR 构建语义相似度图，将 LLM 的模糊描述映射到项目内具体可执行的能力链 (Capability Chains)。
3 Action Runtime 如果允许 LLM 直接输出代码字符串，可能包含注入漏洞或格式错误。需要一个"安全边界"。 将所有提议转化为确定性 API 调用（call(func, args)、ifElse(cond, then, else)），在沙箱中执行，捕获为结构化的动作树。
4 Program Truth (IR) 系统需要一个"世界的真相"——项目中到底有哪些函数、什么类型、怎样调用？这是所有验证的基准。 通过静态分析源代码，提取符号表、类型图、调用图和协议注解。定义了 AI 可以操作的"封闭世界"。
5 Constraint Engine 即使有 IR，如果不检查每个动作，LLM 仍可能"幻想"不存在的函数或传错参数。需要第一道快速防线。 基于 IR 对动作树进行毫秒级规则化验证：SVL-1（函数存在？）、SVL-2（类型匹配？）、SVL-3（变量先声明？）。
6 SSG Validator 前三个 SVL 只检查"代码有没有错"，不检查"行为是否合法"。需要更深层的协议验证。 通过可编程状态机检查 SVL-4：函数调用顺序是否符合业务协议？例如，必须在认证后才能签发令牌。
7 Failure Corpus + Immune Memory 单次拦截还不够。系统需要"记住"每次违规，从中学习，避免重复犯错。这是"越用越聪明"的基础。 每次违规记录到失败语料库（含意图、错误详情、SSG 状态）。从失败模式生成抗体规则，通过信用循环调整函数成功率权重。
8 Counterfactual Engine 光说"你错了"不够，还需要告诉开发者"怎么改才对"。这是 V3 的核心突破。 三种搜索策略（历史语料库、SSG BFS、抗体规则）并行搜索修复方案 → 去重合并 → 特征提取 → 排序 → Top-3 修复方案。
9 Code Emitter 验证通过的动作树仍然是抽象结构，需要最终落地为可编译的源代码。 将动作树确定性翻译为 TypeScript/Python 代码，处理导入、作用域、格式化。含自动修复（编译重试循环）。

第三部分：核心组件详解

3.1 程序真相 (IR) — 系统的"自我模型"

作用：Progmune 的"基因组"。通过 ts-morph（TypeScript Compiler API）静态分析源代码，提取出系统对项目代码的唯一、确定性认知。

组成逻辑：

组件提取内容用途
符号表 (Symbol Table)所有函数名、参数列表、返回类型、JSDoc 注解SVL-1：验证函数是否存在
类型图 (Type Graph)参数类型、返回类型、类型别名SVL-2：验证类型匹配
调用图 (Call Graph)函数间调用关系、调用链SVL-3：验证数据流正确性
协议注解 (Protocol Annotations)@protocol、@requires、@produces 等 JSDoc 标签SVL-4：馈入 SSG 状态机
设计价值：IR 定义了 AI 可以操作的"封闭世界"。AI 无法调用 IR 中不存在的函数——这从源头消除了代码幻觉。IR 是所有后续验证的"真相基准"。

3.2 约束引擎 — 天然免疫层 (SVL-1 ~ SVL-3)

作用：基于 IR 对动作树进行快速、规则化的验证。这是系统的第一道防线——在毫秒级拦截最常见的低级错误。

级别检查内容逻辑失败示例
SVL-1 符号存在性 每个被调用的函数在 IR 的符号表中是否存在？ flushAndClose() → ❌ IR 中无此函数
SVL-2 类型有效性 参数数量和类型是否与声明的签名匹配？ writeFile(path) → ❌ 实际需要 writeFile(path, content)
SVL-3 数据流正确性 变量是否先声明再使用？有无循环引用？ const x = y + 1 → ❌ y 未声明

组成逻辑：SVL-1~3 是"天然免疫"——不依赖历史数据，对所有代码无差别检查。这一层解决的问题是 LLM 幻觉（编造函数名）和粗心错误（参数写错）。由于基于 IR 的确定性格子，不会产生假阳性。

3.3 语义状态图 (SSG) — 获得性免疫层 (SVL-4)

作用：通过可编程状态机，建模系统资源的有效状态及其允许的转移。验证 SVL-4（协议合法性），确保函数调用序列符合业务逻辑。

组成逻辑 — 为什么需要状态机？

SVL-1~3 检查"代码有没有错"，但无法检查"行为是否合法"。例如：

// 以下代码通过 SVL-1~3（函数都存在、类型都对、变量都声明了）
// 但它是危险的——在认证之前就签发了令牌！
generate_jwt(user)    // ❌ 协议违规：需要先 verify_password
create_session(token) // ❌ 协议违规：需要先生成 JWT

StateAnnotation（规则原子）

{
  pre_states: ["UNAUTHENTICATED"],    // 调用前必须存在的状态
  post_states: ["PASSWORD_VERIFIED"], // 调用后激活的状态
  invalidate: ["UNAUTHENTICATED"],    // 调用后消耗的状态（可选）
  namespace: "auth"                   // 所属状态机域
}

验证流程

validateTransition(ctx, "verify_password"):
  1. 查找规则 → pre=["UNAUTHENTICATED"]
  2. 检查前置条件 → 当前状态有 UNAUTHENTICATED? ✓
  3. 应用状态变更:
     - invalidate: 删除 UNAUTHENTICATED
     - post_states: 添加 PASSWORD_VERIFIED
  4. 返回 { valid: true, acquired: [...], invalidated: [...] }

3.4 免疫记忆与失败语料库 — 免疫记忆层

作用：每次约束违规被记录到失败语料库。系统从失败模式中学习，生成"抗体规则"，并通过信用循环调整函数权重。这是"越用越聪明"的机制基础。

组成逻辑 — 三层记忆：

记忆类型存储内容TTL作用
工作记忆当前会话的变量绑定和状态会话级别避免同一会话中重复犯错
情景记忆TrajectoryRecord → 完整的失败/成功轨迹
含意图、违规类型、修复路径、上下文特征		7 天衰减为 CorpusStrategy 提供历史修复数据
语义记忆指纹（修复模式哈希）→ 成功率
边缘拒绝（哪些修复被明确拒绝）		永久为 LearningRanker 提供接受率数据
信用循环 (Credit Loops)：每次函数调用成功或失败，系统更新其成功率权重（含拉普拉斯平滑 + 时间衰减）。在模糊意图下，策略规划器依据这些权重选择最可靠的能力链——系统自动倾向于历史上更成功的函数。

3.5 反事实规划引擎 — "告诉你三条修法"

作用：当验证失败时，系统不仅报告"你错了"，还提供 Top-3 修复方案。这是 V3 的核心突破。

组成逻辑 — 为什么是三层策略？

不同的修复方案来自不同的知识源，各有优势和盲区。三层并行搜索 + 合并去重 + 统一排序，确保覆盖尽可能多的修复可能性：

                           │
            ┌──────────────┼──────────────┐
            ▼              ▼              ▼
     CorpusStrategy   ProtocolStrategy  AntibodyStrategy

3.6 代码发射器 — 程序落地层

作用：将所有验证通过的动作树确定性翻译为可执行的 TypeScript 代码。处理导入、变量作用域、嵌套结构缩进等。

自动修复：发射器内含编译重试循环——如果生成的代码编译失败，自动分析错误模式（如缺少导入、类型错误）并修复，最多重试 5 次。

设计价值：确保从动作树到源代码的翻译是确定性的。同一个动作树永远生成同一份代码。

4.1 覆盖率引擎与协议前沿 (P3)

组成逻辑：

  • 解析阶段：从 59 条协议规则中提取全部 26 个状态和 105 个理论转换
  • 追踪阶段：遍历 2,385 条轨迹，标记已观测的状态和转换

4.2 奖励系统与学习排序 (P4)

作用：从历史反馈中学习哪些修复候选更好。这是"越用越聪明"的量化实现。

LearningRanker（反馈修正排序）

// 带预训练模型:
adjustedScore = baseScore×0.7×0.5
  + effectiveReward×0.3×0.3
  + modelScore×modelWeight

// 仅遥测（无模型）:
adjustedScore = baseScore×0.7
  + effectiveReward×0.3

effectiveReward = 0.5×acceptanceRate
  + 0.5×executionSuccessRate

关键设计：accepted ≠ good。学习 acceptance + execution success 组合信号，防止系统"学坏"——偏爱快速但有泄漏的修复。

LogisticRewardModel（预训练模型）

模型参数:
  learningRate: 0.01

训练数据: 2,385 条轨迹
最终损失值: 0.18

  latencyCost: 0.77

含义：模型已学习到——更快、更简洁的修复方案更可能被接受。

4.3 协议学习 (P6) — 从观察中发现规则

软件物理引擎 (P6.2)：通过 73 个物理关键词将函数名映射为软件物理模式。不关心函数叫什么——关心它做了什么。跨 5 个仓库分析：平均覆盖率 75%，平均相似度 67%。结论：STRUCTURE_LEARNED。

无监督协议发现 (P6.3)：从调用序列中提取结构指纹 → 基于编辑距离聚类 → 提取中心原型 → 推断状态机模式 → 计算闭环率作为置信度。整个过程零关键词匹配，完全基于结构特征。

自动协议合成器 (P6.4)：将发现的轨迹聚类转换为可执行的 SSG 协议规则。当前合成 4 个协议、14 条规则、零冲突、治理就绪。

4.4 拓扑表示与新协议类型 (P7)

P7.1 名称混淆：0% 存活。证明 V5 之前的系统学的是"动词"（函数名），而非"结构"（状态机拓扑）。

P7.2 拓扑表示：90% 存活。通过图指纹（节点数、边数、度分布、直径、DAG），系统在不依赖函数名的情况下达成跨仓库 90% 相似度。这是协议拓扑学习的第一个真实证据。

P7.3 五种新协议类型：从线性协议拓展到非线性拓扑，覆盖真实世界中的各类 API 模式。

协议类型规则数拓扑形状核心机制代表性函数
Stateless 8 孤立节点（无状态变更） empty pre_state + empty post_state = 可随时调用 compute_hash, validate_schema, sanitize_input, encode_payload
Transaction 10 含分支 DAG（开始→操作→提交/回滚） 自转换操作 + 保存点子状态 + 两阶段提交 begin_tx, commit_tx, rollback_tx, savepoint_create, prep_two_phase
Conditional 9 含 5 分支的树（评估→TRUE/FALSE/短路/重试/升级） 分支选择 + 多条件退出 + 审计 evaluate_access, grant_access, deny_access, escalate_access, audit_condition
Loop 9 含自转换的循环（获取→处理→迭代/退出） 自转换迭代 + 超时/重试退出 + 轮询 init_fetch_loop, fetch_batch, process_item, next_iteration, exit_loop
Cross-Protocol 6 桥接（连接多个命名空间） 认证门控 + 资源访问桥 + 跨命名空间状态转换 auth_file_open, auth_db_connect, auth_db_query

为什么需要这些新类型？原有 4 种线性协议（auth/file/db/dev_pipeline）只能覆盖 ~88 条轨迹。新增 5 种非线性协议类型后，随机游走可生成 2,385 条轨迹——语料库增长 27 倍，且覆盖了真实 API 中常见的事务、条件分支、循环迭代和跨域访问模式。

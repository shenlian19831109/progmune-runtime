Progmune — AI Software Verification Infrastructure

投资人白皮书 v3.2 | 2026 年 8 月

一句话：Progmune 验证 AI 生成的代码是否遵循正确的协议生命周期——这是 SAST 和 SCA 都看不到的盲区。

1. 问题：AI 生成代码的隐性风险

AI 编码助手（Claude Code, Cursor, Copilot）正在被数千万开发者使用。但它们生成的代码有一个系统性问题：协议生命周期错误。

SAST 工具检查单条语句（SQL injection, XSS）
SCA 工具检查已知 CVE
没有人检查"这个函数调用序列是否遵循了正确的协议？"

真实案例：

  • 支付漏洞：AI 生成了支付确认代码，但跳过了回调签名验证——钱收到了，但不知道是谁付的
  • 认证绕过：JWT 在密码验证之前就被签发——任何人拿到 token 就能访问
  • 资源泄漏：文件打开后从未关闭，数据库连接从未断开

这些都是跨函数调用的序列问题，不是单行代码 bug。传统工具完全看不到。

2. 方案：协议状态机验证

Progmune 用协议状态机（Protocol State Machine）来验证函数调用序列。

真实代码:  bcrypt.compare(password, hash) → jwt.sign(payload) → res.cookie(token)
              ↓ 别名映射                    ↓ 别名映射            ↓ 别名映射
协议规则:  verify_hash ──────────────→ generate_jwt ────────→ create_user_session
              │                              │                      │
状态机验证: PASSWORD_VERIFIED ──→ TOKEN_ISSUED ──→  SESSION_CREATED
              │
        如果 bcrypt.compare 被跳过 → state 停留 UNAUTHENTICATED → generate_jwt 无法执行 → 违规报告

核心机制：

  • 144 条协议规则，每条定义 pre_states → post_states → invalidate 的状态转移
  • 226 个库别名：bcrypt.compare → verify_hash，jwt.sign → generate_jwt，express.listen → http_create_server
  • 27 个命名空间：auth, registration, tls, payment, file, db, transaction, session_mgmt 等
  • BFS 修复路径：不仅检测违规，还计算"要插入哪个函数"才能修复

框架结构分析能力

4.3 修复能力

fix() 不再是 stub——它是一个端到端的修复管道：

  1. 检测：SSG 状态机 + 框架适配器发现违规
  2. 建议：BFS 计算缺失的函数调用序列（如 "load_tls_config"）
  3. 应用：在源码中找到违规行，插入修复代码（带正确缩进）
  4. 验证：重新运行 SSG 确认违规已消除

4.4 知识网络验证

跨项目知识转移实验（3 个 Express 项目）：

  • ✅ 库级别别名转移成立：bcrypt.compare → verify_hash 在任何使用 bcrypt 的项目中都有效
  • ❌ 项目包装函数不转移：内部函数（createSessionToken 等）需要 .progmune_aliases.json
  • 结论：每新增一个使用新库的项目，所有使用该库的项目的验证都变强。

5. 竞争格局

工具检测什么Progmune 的差异
CodeQL / Semgrep单语句模式（SQL injection, XSS）Progmune 检测跨函数序列——"这个序列是否遵循了协议？"
Snyk / Dependabot已知 CVE（依赖版本）Progmune 检测 AI 生成的新代码，不是已知漏洞
SonarQube代码异味、复杂度Progmune 验证行为正确性——"做了该做的事吗？"
ESLint语法/风格规则Progmune 验证协议合规性——"按正确的顺序做了吗？"

Progmune 是互补的，不是替代品。它填补了"函数调用序列验证"这个空白——SAST、SCA、linter 都看不到的维度。

Progmune — AI Software Verification Infrastructure

投资人白皮书 v3.2 | 2026 年 8 月

一句话：Progmune 验证 AI 生成的代码是否遵循正确的协议生命周期——这是 SAST 和 SCA 都看不到的盲区。

1. 问题：AI 生成代码的隐性风险

AI 编码助手（Claude Code, Cursor, Copilot）正在被数千万开发者使用。但它们生成的代码有一个系统性问题：协议生命周期错误。

SAST 工具检查单条语句（SQL injection, XSS）
SCA 工具检查已知 CVE
没有人检查"这个函数调用序列是否遵循了正确的协议？"

真实案例：

  • 支付漏洞：AI 生成了支付确认代码，但跳过了回调签名验证——钱收到了，但不知道是谁付的
  • 认证绕过：JWT 在密码验证之前就被签发——任何人拿到 token 就能访问
  • 资源泄漏：文件打开后从未关闭，数据库连接从未断开

这些都是跨函数调用的序列问题，不是单行代码 bug。传统工具完全看不到。

2. 方案：协议状态机验证

Progmune 用协议状态机（Protocol State Machine）来验证函数调用序列。

真实代码:  bcrypt.compare(password, hash) → jwt.sign(payload) → res.cookie(token)
              ↓ 别名映射                    ↓ 别名映射            ↓ 别名映射
协议规则:  verify_hash ──────────────→ generate_jwt ────────→ create_user_session
              │                              │                      │
状态机验证: PASSWORD_VERIFIED ──→ TOKEN_ISSUED ──→  SESSION_CREATED
              │
        如果 bcrypt.compare 被跳过 → state 停留 UNAUTHENTICATED → generate_jwt 无法执行 → 违规报告

核心机制：

  • 148 条协议规则，每条定义 pre_states → post_states → invalidate 的状态转移
  • 226 个库别名：bcrypt.compare → verify_hash，jwt.sign → generate_jwt，express.listen → http_create_server
  • 27 个命名空间：auth, registration, tls, payment, file, db, transaction, session_mgmt 等
  • BFS 修复路径：不仅检测违规，还计算"要插入哪个函数"才能修复

4.3 修复能力

fix() 不再是 stub——它是一个端到端的修复管道：

  1. 检测：SSG 状态机 + 框架适配器发现违规
  2. 建议：BFS 计算缺失的函数调用序列（如 "load_tls_config"）
  3. 应用：在源码中找到违规行，插入修复代码（带正确缩进）
  4. 验证：重新运行 SSG 确认违规已消除

4.4 知识网络验证

跨项目知识转移实验（3 个 Express 项目）：

  • ✅ 库级别别名转移成立：bcrypt.compare → verify_hash 在任何使用 bcrypt 的项目中都有效
  • ❌ 项目包装函数不转移：内部函数（createSessionToken 等）需要 .progmune_aliases.json
  • 结论：每新增一个使用新库的项目，所有使用该库的项目的验证都变强。

5. 为什么 SAST 和 SCA 不够

传统工具的本质是"比对"——把代码和一个已知的库做比较。Progmune 的本质是"验证"——检查代码是否按正确的协议序列执行。

5.1 SAST — 比对已知攻击模式

SAST 把代码解析成 AST、控制流图、数据流图，然后运行规则引擎——每条规则描述了一种已知的攻击模式。

能检测什么怎么检测的本质
exec(userInput) — 命令注入规则库有"exec + 未转义变量"模式代码模式 ↔ 已知风险规则
innerHTML = x — XSS数据流追踪"未转义变量 → DOM 赋值"污点传播 ↔ 危险汇点
const KEY = "sk-..." — 硬编码密钥正则匹配密钥格式文本模式 ↔ 密钥正则
yaml.load(input) — 不安全反序列化规则库有"yaml.load + 用户输入"模式函数名 ↔ 敏感函数列表

SAST 的局限：它能告诉你"第 42 行的 innerHTML 赋值可能被 XSS 利用"——因为规则库里有这条规则。但它不能告诉你"登录函数里先调了 jwt.sign() 后调了 bcrypt.compare()"——因为没有任何单行代码是错的。错误在于两行代码的顺序。SAST 的规则库不包含跨语句序列规则。

5.2 SCA — 比对已知漏洞数据库

SCA 解析依赖清单，提取名称和版本，查询公共漏洞库。

能检测什么怎么检测的本质
lodash@4.17.15 → CVE 原型污染版本号 ↔ NVD 数据库依赖版本 ↔ 已知 CVE
GPL 依赖在专有项目中许可证字符串 ↔ 策略规则许可证 ↔ 合规策略
3 年前未更新的依赖发布时间 ↔ 当前日期版本时间戳 ↔ 过期阈值

SCA 的局限：它能告诉你"你用的库有一个已知漏洞"——因为 CVE 数据库里有记录。但它不能告诉你"你的代码用 jsonwebtoken.sign() 之前忘了验证密码"——因为这不是已知漏洞，是你写出来的新问题。

5.3 SAST 和 SCA 都看不到的

SAST 能看到（单行模式）
  • exec(userInput) ← 危险函数调用
  • innerHTML = x ← 危险 DOM 操作
  • const key = "sk-..." ← 硬编码密钥
  • yaml.load(input) ← 不安全函数
只有 Progmune 能看到（跨语句序列）
  • jwt.sign() 在 bcrypt.compare() 之前 ← 顺序错误
  • createOrder() 在 estimateCost() 之前 ← 缺少步骤
  • file.open() 后从未 file.close() ← 资源泄漏
  • multer.upload() 在 passport.auth() 之前 ← 中间件顺序

5.4 三种工具的本质区别

SASTSCAProgmune
比对什么代码模式 ↔ 攻击模式库依赖版本 ↔ CVE 数据库调用序列 ↔ 协议状态机
检测粒度单行语句依赖项跨函数序列
知识来源安全专家写的规则公开漏洞报告协议定义 + 别名映射
能否检测新问题不能——只能匹配已知模式不能——只能匹配已知 CVE能——验证序列是否遵循协议
典型输出"第 42 行可能有 SQL 注入""lodash 4.17.15 有 CVE-2019-10744""jwt.sign() 缺少前置的 bcrypt.compare()"

Progmune 是互补的，不是替代品。SAST 有规则库，SCA 有 CVE 库，但没有人有"协议序列规则库"——这就是 Progmune 的品类。三者覆盖代码安全的不同维度。

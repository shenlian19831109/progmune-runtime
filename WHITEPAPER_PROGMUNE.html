Part A · 基础免疫 (V2.5)

第三章 · 基础免疫层

3.1 IR（中间表示）— 系统的"自我模型"

解决什么问题

LLM 生成代码时基于"开放世界假设"——它不知道项目中实际存在哪些函数、哪些类型、哪些状态约束。这导致四种结构化错误（SVL-1~4）。

方法：从源文件静态提取完整的符号表、类型图、调用图、能力元数据，构建项目的"数字孪生"——一个精确反映项目真实结构的中间表示。
效果：519 函数完整索引；purpose 100% 覆盖；produces 62%；requires 46%。约束引擎基于 IR 可在毫秒级拒绝 SVL-1/2/3 违规。
五层自动元数据派生策略
策略方法覆盖率提升
S1 协议映射@protocol pre_states → @requires直接映射
S2 函数名推断驼峰拆分 → @purpose30% → 100%
S3 文件路径标签目录结构 → @tags94% → 100%
S4 前缀推导load* → DATA, format* → FORMAT+20%
S5 调用图传递显式注解沿调用链继承+5%

3.2 约束引擎 — 天然免疫

解决什么问题

事后校验和 RAG 只能降低错误概率，无法提供形式化保证。需要一种确定性的、可证明正确的验证机制。

方法：将 LLM 输出封装为受限动作树（call/assign/ifElse），在沙箱中执行前先通过三层快速规则验证。
原理：天然免疫不学习 — 它是硬编码的模式匹配。优势是 100% 确定性，劣势是只能识别已知的违规模式。
效果：毫秒级 SVL-1/2/3 验证。0 假阳性（合法代码永不误拒）。

3.3 SSG 协议引擎 — 获得性免疫

AuthProtocol 状态转移图： UNAUTHENTICATED │ │ verify_password ▼ PASSWORD_VERIFIED │ │ generate_jwt [inv: PASSWORD_VERIFIED] ▼ TOKEN_ISSUED │ ├── create_session → SESSION_ACTIVE [inv: TOKEN_ISSUED] │ │ │ │ logout → UNAUTHENTICATED [inv: SESSION_ACTIVE] │ └── revoke_token → UNAUTHENTICATED [inv: TOKEN_ISSUED]

解决什么问题

代码不仅需要语法正确，还需要遵循资源状态的生命周期规则。例如：不能在没有打开文件时写入；不能在未认证时签发 JWT。这些规则无法在编译时检查。

方法：每个函数声明前置状态（pre_states）、后置状态（post_states）和失效规则（invalidate）。验证器在处理动作序列时模拟状态转移，拒绝前置条件不满足的调用。同时执行 Invariant-2 Delta 合法性验证：确保每个 acquired 状态在函数 post_states 中，每个 invalidated 状态在函数 invalidate 列表中。
原理：受生物 MHC 分子抗原呈递机制启发。SSG 不是静态规则 — 它是可编程的状态机。新增协议不需要修改验证器，只需添加状态定义。
效果：增量验证 0.05ms/步；全量账本审计 3ms；Invariant-0/1/2 三重一致性保证。

3.4 Failure Corpus + 抗体系统 — 免疫记忆

知识回流三层架构 (L1→L2→L3)： Failure Corpus ──→ getLearnedPatterns() │ ┌─────────────────┼─────────────────┐ ▼ ▼ ▼ L1: 提示注入 L2: 快速通道 L3: 信用评分 ACL-3+ 抗体 ACL-4 抗体 Laplace 平滑 注入 Planner 0 LLM 调用 所有权重函数 Prompt 直接构建序列 SVL 惩罚 + 衰减 │ │ │ ▼ ▼ ▼ 效果: 历史警告 效果: 90% 绕过率 效果: 冷启动 0.5

解决什么问题

V2.5 之前，系统记录失败但不学习。同样的错误可以反复出现。需要一种机制将失败经验转化为预防能力。

方法：三层记忆架构（工作/情景/语义）。Failure Corpus 记录每次违规的模式和修复路径。Antibody Registry 按发生频率和意图多样性计算 ACL 等级（ACL-1~4）。L1 注入提示、L2 快速通道、L3 信用加权。
原理：Laplace 平滑解决小样本偏差（1/1 成功不再虚高为 1.0 → 0.67）。SVL 惩罚系数（SVL-4 = 3.0x）确保高危违规优先防御。时间衰减半衰期 1 天使系统适应变化。
效果：SVL-1/2/3 抗体稳定匹配；ACL-4 快速通道 90% 绕过 LLM；免疫修复率 70%。
Part B · 规划与反事实推理 (P2)

第四章 · 反事实规划器

4.1 定位：从"你错了"到"这里有三种修法"

解决什么问题

V2.5 的验证器在违规发生时只能说"你错了"——它能检测协议违规，但无法提供结构化的修复建议。用户需要自己推断修复路径。反事实规划器填补了验证与修复之间的 gap。

4.2 架构：Strategy → Candidate → Ranker 三层解耦

Counterfactual Planner 完整数据流： Goal / Violation │ ┌────────────┼────────────┐ ▼ ▼ ▼ Corpus Protocol Antibody Strategy Strategy Strategy (经验搜索) (协议推理) (免疫规则) │ │ │ ▼ ▼ ▼ Candidate[] Candidate[] Candidate[] └────────────┼────────────┘ ▼ deduplicateCandidates() 合并同签名候选 + 跨源证据 │ ▼ FeatureExtractor 7 维特征向量 │ ▼ LinearRanker safety | performance | auditability | overall │ ▼ Top-3 Repairs
关键设计原则
策略只产生候选，不打分。每个策略实现 CandidateSearchStrategy 接口，返回零分候选。评分是 Ranker 的独立职责。这确保：新增策略（如 LLMRepairStrategy）无需修改任何 Ranking 代码；替换排序器（如 RewardModelRanker）无需修改任何 Strategy 代码。接口隔离是 P2 架构最核心的决策。

4.3 三个搜索策略详解

CorpusStrategy 经验

方法：从 Failure Corpus 中加载所有 violation/repair 轨迹，按修复路径分组去重，根据证据数量和成功率生成候选。
原理：历史是最好的老师。如果同一个修复在过去成功了 42 次，它很可能再次成功。
效果：高置信度（多证据）；冷启动脆弱（新错误无历史）。

ProtocolStrategy 推理

方法：基于 SSG 协议图进行 BFS，从当前状态搜索到达目标状态的合法路径。P3.10 新增 Goal Template（自然语言→函数链）。P3.14 新增 Frontier Explorer（纯状态搜索，不依赖模板）。P3.15 新增跨协议桥接。
原理：协议是确定性的 — 如果规则中有 close_file，就一定能找到它。不需要训练数据。
效果：零数据依赖；资源清理总能发现；受规则数量限制。

AntibodyStrategy 免疫

方法：从抗体注册表中匹配违规类型和协议，使用学习到的免疫规则直接生成修复建议。
原理：经过充分验证的抗体（ACL-3+）具有高置信度。这是将 V2.5 的免疫记忆直接转化为 P2 的修复候选。
效果：ACL-4 抗体 90% 绕过 LLM；依赖失败积累。

4.4 跨源证据合并

同一修复路径（"close_file"）可能同时来自 Corpus、Protocol BFS 和 Antibody。合并后：

evidenceSources: ["corpus", "protocol", "antibody"]
evidence: max(42, 0, 0) = 42  // 取最大证据数

多源验证的修复比单源修复可信度更高。这是 Reward Model 的关键输入特征。

4.5 排序器：七维特征 + 四种模式

特征含义计算方法
protocolSafety路径安全约束满足度约束匹配率 × 0.4 + 路径长度惩罚 × 0.6
historicalSuccessRateCorpus 历史成功率从 TelemetryIndex 查询
actionCount修复路径动作数actions.length
latencyCost延迟成本（逆）min(1, actionCount / maxActions)
auditability可审计性1 - actionCount / maxActions（路径越短越可审计）
corpusEvidence语料库证据数量从 metadata 提取
source来源策略corpus / protocol / antibody
overallScore = 0.4×safety + 0.3×successRate + 0.2×performance + 0.1×auditability

四种模式对应不同用户场景：rankSafety()（金融系统 — 最安全）、rankPerformance()（实时系统 — 最快）、rankAuditability()（合规团队 — 最可审计）、rankOverall()（默认加权）。

Part C · 学习系统 (P2.5-2.6)

第五章 · 从反馈中学习

5.1 Telemetry：决策数据管道

解决什么问题

规则系统无法自我改进。不知道哪个策略更有效、哪种修复更受用户欢迎。需要一套完整的数据采集和分析系统，将每一次 Planner 决策转化为可量化的反馈信号。

方法：PlannerTelemetry 记录每个决策的完整生命周期（Goal → Candidates → Selected → Feedback → Execution）。TelemetryIndex 使用 Map<fingerprint, CandidateStats> 实现 O(1) 统计查询。RepairLifecycle 追踪 proposedAt → acceptedAt → executedAt → executionSucceeded 完整链。
原理：RLHF（Reinforcement Learning from Human Feedback）需要标准化的数据格式。Progmune 的 Telemetry 层在系统级别实现了这一格式 — 每个 RepirLifecycle 就是一个 (state, action, reward) 元组。
效果：1000 决策模拟仪表盘实时输出策略/协议/目标接受率；O(1) 指纹查询；JSONL 持久化。

5.2 LearningRanker：从接受到学习

解决什么问题

LinearRanker 使用固定的人工权重。它不知道哪些修复历史上被用户接受、哪些被拒绝。需要一种机制让排序器能够从反馈数据中学习。

方法：LearningRanker 包裹基础 Ranker，从 TelemetryIndex 查询每个候选的有效奖励，重新加权排序。核心公式：
effectiveReward = 0.5 × acceptanceRate + 0.5 × executionSuccessRate
adjustedScore  = baseScore × 0.7 + effectiveReward × 0.3
原理：accepted ≠ good — 这是最关键的架构决策。用户可能大量接受快速但泄漏资源的修复（因为快）。如果只学 acceptance，系统会越来越倾向于有缺陷的快速方案。组合 acceptance + execution success 双重信号来防止"学坏"。
效果：已通过 Ranking Evolution Test 证明自进化回路：Phase 1: A(safe) 接受 90 次 → A 排第一；Phase 2: B(fast) 连续接受 100 次 + 执行成功 → B 反超 A。离线排序准确率 +66.7%。
Ranking Evolution Test — 自进化回路证明
Phase 1: A (safe, 90 accepts, 100% execution)  vs  B (fast, 10 accepts, 30% execution)
  → effectiveReward: A=1.0, B=0.65
  → A 排第一 ✅

Phase 2: B 连续接受 100 次 + 执行成功
  → B acceptance 反超
  → effectiveReward: B=0.97, A=1.0
  → B 排第一 ✅ (反馈超越了启发式)

6.1 Benchmark System

解决什么问题

没有基准就没有进步。每次改进 Planner 或 Ranker 后，需要一套标准化的测试来量化效果。

方法：7 个协议文件，49 个基准用例，覆盖 6 种违规类型（resource_leak, missing_prerequisite, illegal_state_transition 等）。每个用例定义：goal（自然语言目标）、broken（错误序列）、expected（正确序列）、violationType（违规类型）。
当前基线：Top-1: 14% | Top-3: 39% | Avg Latency: 19.9ms | Avg Candidates: 2.5

6.2 Error Budget Dashboard

解决什么问题

知道 Top-1=14% 不够 — 需要知道为什么。Error Budget 将 49 个失败按根本原因归类，告诉团队下一阶段的研发优先级。

方法：对每个基准失败进行根本原因分类：候选存在但排错序（bad_ranking）？候选不存在（missing_candidate）？协议模型找不到路径（bad_protocol_model）？目标解析失败（goal_mismatch）？历史数据不足（insufficient_history）？
Reason                  Count   Pct
────────────────────────────────────
  missing_candidate        28    57%  ← 候选发现是瓶颈
  bad_ranking               9    18%  ← 候选存在但排错序
  bad_protocol_model        0     0%  ← 已归零（协议推理层稳定）
  insufficient_history      5    10%
  success                   7    14%
原理：57% missing_candidate 揭示了一个关键事实 — 问题不是排序，而是候选生成。协议推理层已稳定（0% bad_protocol_model），剩余瓶颈在于函数存在但状态未连接的转移缺口（92% 是 missing_transition，8% 是 missing_action）。
结论：P0 优先级 = 候选发现（而非 Reward Model 或 Ranking）。

6.3 Data Quality Layer

解决什么问题

原始接受数据不可信 — 用户接受 ≠ 修复正确。39% 的反馈数据显示 accepted 与 execution success 矛盾。如果将这些数据直接用于训练，Reward Model 会学歪。

方法：三重验证信号分离 — 原始接受（accepted）、执行结果（executionSucceeded）、SSG 验证通过（postValidationPassed）、回归测试通过（regressionTestsPassed）。未经验证的数据使用中性先验 0.5。
rewardSignal = accepted×0.4 + validationPassed×0.4 + executionSucceeded×0.2
(no verification data → return 0.5 neutral prior)
效果：检测到 39% 矛盾数据；质量评分平均 79%；为 P4 Reward Model 提供干净的训练信号。

Part E · 候选发现 (P3.10-3.15)

第七章 · 打破候选发现瓶颈

7.1 Goal-conditioned Planner

解决什么问题

ProtocolStrategy BFS 只能从当前状态出发搜索，无法理解"logout user"需要先完成整个认证流程。缺少将高层目标映射到底层函数序列的能力。

方法：22 个 Goal Template — 每个模板定义一个目标模式（正则）、协议命名空间、前置条件链。
"logout user"      → [verify_password, generate_jwt, create_session]
"safely write"     → [open_file, write_file]
"query database"   → [connect_db, query_db]
效果：insufficient_history 从 39% → 14%。局限：手动维护，无法覆盖未定义的变体。

7.2 Frontier Explorer

解决什么问题

Goal Template 需要手动编写，覆盖率受模板数量限制。例如"force_logout"不在模板中就无法处理。

方法：纯 BFS 状态图搜索 — 不依赖任何模板。输入当前状态集合 + 目标状态集合，输出最短合法路径。
searchFrontier(rules, ["UNAUTHENTICATED"], ["SESSION_ACTIVE"])
  → ["verify_password","generate_jwt","create_session"] (3步)
searchFrontier(rules, ["FILE_OPEN"], [])
  → ["close_file"] (1步 — 资源清理)
原理：协议规则是确定性的有向图。BFS 保证找到最短路径。多起点搜索（searchFrontierMulti）尝试不同初始状态组合。探索模式（exploreFrontier）生成多条可选路径供排序器选择。
效果：bad_protocol_model 从 6% 永久归零。任何状态对都能被搜索。这证明协议推理层已完全稳定。

7.3 Cross-Protocol Planner + Search Trace

Cross-Protocol Bridges

方法：定义协议间桥接 — AuthProtocol(SESSION_ACTIVE) → FileProtocol(INIT) → DBProtocol(INIT)。从跨协议失败中推断新桥接。
效果：支持"auth → file → db"多协议修复链。

Search Trace

方法：记录每次搜索的详细过程 — 展开节点、死胡同原因（missing_action/missing_transition/depth_limit/bridge_missing）、是否生成候选。
效果：将 57% missing_candidate 分解为可操作的子原因。
Part F · 知识演化 (P3.16-3.23)

第八章 · 系统自我扩展

8.1 Gap Mining + Transition Synthesizer

解决什么问题

协议规则靠手工编写，覆盖面永远有限。当 57% 的失败源于"候选找不到"时，真正的问题可能是：协议规则本身不完整。需要一种机制来自动发现并补全缺失的协议知识。

方法： Gap Analyzer（P3.16）：分析基准失败 → 提取期望修复链中的函数 → 检查是否存在于协议规则中 → 不存在 = missing_action；存在但状态未连接 = missing_transition。 Transition Synthesizer（P3.18）：对 consecutive function pairs 检查是否有 post_state→pre_state 连接 → 无连接则推断为新转移。置信度 = evidenceCount / maxEvidence。
发现：12 个缺口（1 missing_action + 11 missing_transitions）。92% 是 missing_transition — 函数都在，但状态图没连起来。首次自动推断：open_file → flush_file (FILE_OPEN → FILE_DIRTY, 100% confidence)。

8.2 Knowledge Governance

解决什么问题

自动推断的知识可能不可靠。2 个基准案例的共识 ≠ 真实正确。需要一套治理机制来验证、版本化、回归测试每一条自动生成的协议知识。

方法：三层治理： P3.21 Inference Validator — 多源验证（benchmark ≥ 3 + trajectory ≥ 5 + contradiction = 0 → verified）。 P3.22 Knowledge Patch Store — 每条推断是版本化补丁。Planner 读取 Base Rules + Approved Patches（从不修改原始文件）。支持 audit/rollback/diff。 P3.23 Regression Test — 对每个 proposed patch 跑全量基准。仅当 Top-1 和 Top-3 不退化时自动批准。
原理：错误的知识 + 完美的 Reward Model = 高置信度地做错事。正确的知识 + 普通 Ranker = 稳定提升。知识治理是学习系统的基础设施 — 没有它，自动演化就是随机漂移。
Governance Pipeline:
  Synthesize → Validate → Propose → Regression Test → Auto-Approve

Report: Proposed 1 | Approved 1 ✅ | Rejected 0
  ✅ revoke_token → create_session (no regression)
Part G · 偏好学习 (P3.11-13, P3.24-27)

第九章 · 从点到对的质变

9.1 Pairwise Preference — RLHF 数据原语

解决什么问题

accepted/rejected 太粗糙。用户可能拒绝了正确但慢的方案，也可能接受了错误但快的方案。需要更细粒度的偏好信号：A 比 B 好在哪？

方法：RepairPreference { winner, loser, goal, protocol } — 这是 RLHF（Reinforcement Learning from Human Feedback）的标准化数据格式。PreferenceRanker 使用 winRate（来自历史配对比较）结合 heuristicScore（来自 LinearRanker）排序。
PreferenceRanker.score = winRate × 0.6 + heuristicScore × 0.4
原理：Pointwise（accepted/rejected）只能学"这个好不好"。Pairwise（A > B）能学"这两个哪个更好" — 这是训练 Reward Model 所需要的监督信号格式。

9.2 Ranker Stress Test

增强型基准：expectedTop1（必须排第一）、acceptableTop3（可接受的前三）、unacceptableRepairs（绝对不能出现）。测试排序器区分可接受修复与不可接受修复的能力。

9.3 Discovery Benchmark + Counterfactual Replay

Discovery Benchmark

三层指标：Discovery Rate（至少一个正确候选？）→ Top-3（排序质量）→ Top-1（最佳选择）。比单一指标更精准定位瓶颈。

Counterfactual Replay

用历史决策数据离线评估新排序器/新 Frontier。Baseline 33.3% → Learning 100% (+66.7%)。证明反馈数据中存在可学习信号。

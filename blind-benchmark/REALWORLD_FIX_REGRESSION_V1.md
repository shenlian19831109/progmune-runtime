## 二、这是对「能力 vs 语料」问题的实证回答

两轮 AI 生成项目验证（V1 open-seo 10 flags 全 FP、V2 skyvern 181 flags 全 FP）留下一个悬而未决的问题：**0 检出是因为代码干净，还是引擎看不见？** 本实验用「真实发生过的病」消除该歧义——结论明确：

> **是能力面问题。8 个真实存在的认证/授权/文件路径类 bug，引擎一个都抓不到。**

且这些 bug 不是边角类型——OAuth 身份绑定绕过（CVE-2026-87016）能让攻击者登录为管理员，正是 Progmune 宣称要验证的「协议生命周期」核心面。

## 三、漏报根因（按类别——每一类都是一项能力缺口）

| 类别 | 条目 | 根因 |
|---|---|---|
| **查询语义** | fr-001 | `.contains()`（SQLite LIKE 通配）vs 精确匹配——SQLAlchemy 查询构造语义，调用序列状态机与词表规则均不可见 |
| **策略逻辑分支** | fr-002, fr-003 | 漏洞 = 某条代码路径（令牌交换/白名单检查）**少了一次检查调用**——状态机只能检「调用顺序错」，检不出「该有的调用没有」 |
| **数据流（凭据流向）** | fr-004 | cookie 被放入发往第三方服务器的请求——凭据数据流追踪，无此规则面 |
| **数据流（归属比较）** | fr-005 | 写路径缺少 ownerId 比较——TS 侧有 ownership 规则（paramGated），open-webui 该形态未触发/无对应 Python 面 |
| **配置与通道路由** | fr-006 | 服务端通道未做平台级授权——配置层+通道路由逻辑 |
| **语言面缺口** | fr-007 | 路径穿越规则 `languages: ["python"]`——TS 项目结构性不覆盖 |
| **密码学协议语义** | fr-008 | attestation 验证完整性——无此规则面 |

## 四、已有收获（不是零和）

1. **语料本身逼出了两个真实词汇缺口并已修复**：扫描 open-webui 时发现其主力认证依赖 `get_verified_user`/`get_admin_user` 不在 AUTH_WORDS → 142 条框架层误报 → 词表补上后消除（open-webui 542 路由剩 17 条全为公开设计端点）。加上 skyvern 的 `get_current_org` 族——**框架层认证词汇缺口是一个反复出现的系统性缺陷，每进一个新语料就暴露一批**。
2. **边界确认**：fastapi-realworld 0 FP、skyvern 2 FP 在词表修改后保持；盲测 64/64、C 金标 F1=95.7%、Go 盲测 P=R=100% 零漂移。
3. **方法成立**：修复回归管线（公告→commit→parent 快照→扫描→真值比对）跑通，后续任何引擎改动都可以用这套基准测召回——不再靠「挑了什么人群」叙事。

## 五、结论与决策点（供用户拍板）

**结论：当前引擎的检出面 = 调用序列状态机 + 词表/结构规则。真实世界安全修复的主流形态（查询语义、数据流、策略分支、密码学细节）全部在检出面之外。** 精度修复（阶段 1）把误报压下来了，但召回面没变——「更安静」不等于「能看见」。

三个方向（可组合）：
- **A. 扩检测面**：按漏报根因类别逐项立项。可行性排序：fr-007 路径穿越 TS 化（Python 标记管线已有，移植成本最低）> fr-005 归属校验 Python 化（TS 侧规则可参照）> fr-001 查询语义（需 SQLAlchemy 查询建模，中型工程）> fr-004 凭据数据流（大工程）。
- **B. 收窄承诺**：把产品承诺从「检出协议违规」收窄到实测能检出的面（调用序列违规），修复回归作为持续基准，每扩一项能力就补一条真实修复进语料。
- **C. 加样本**：8 条样本集中在 6 条 open-webui，需扩 pip/npm 独立项目（子代理额度恢复后可继续），确认漏报分布不是单仓库偏差。

**建议：A 与 B 并行**——按可行性序逐个扩面（先 fr-007/fr-005 这两个最接近现有管线的），每个新能力用「先加语料→再写规则→修复回归复测」闭环验收；同时按实测数据更新定位文档，不写超出检出面的承诺。

摘要

Progmune Runtime 提出一种新范式：程序免疫学 (Program Immunology)——确保 AI 生成代码安全可靠的系统性方法。受生物免疫系统分层防御机制的启发，Progmune 构建了一个约束导向的程序合成运行时，在多个层级上强制执行语义有效性：从符号存在性和类型兼容性，到数据流正确性和协议合法性。系统将大语言模型从不受约束的代码生成器，降级为在程序中间表示（IR，即"程序真相"）所定义的封闭世界中运行的受限启发式提议器。

核心理念：以免疫保障生成，以生成驱动免疫。

v3 引入三个关键突破：(1) LLM+Graph 联合架构——LLM 跨语义鸿沟选种子，Capability Graph 做数据流路由连成链，在 132 函数的语义鸿沟挑战中达到 90% 精度；(2) 知识反馈回路闭环——L1/L2/L3 三层抗体机制从 Failure Corpus 自动生成后回流到规划器，改变代码生成行为；(3) Self-Hosting 验证——Progmune 首次使用自己的能力生成了 10 个功能模块，证明了 Pipeline 的完整闭环。

v3 的核心命题转移：从"构建知识层"转向"证明知识层改变结果"。Runtime 层已近成熟（~95%），知识层的真实 ROI 成为唯一的验收标准。

一、问题声明：AI 代码生成中的开放世界谬误

1.1 四类典型错误

大语言模型在生成代码时，隐含地基于开放世界假设运行：训练数据中见过的任何函数、库或 API 模式都被假定在当前上下文中可用。这一假设导致四类典型错误：

级别错误类型示例后果
SVL-1符号幻觉调用项目中不存在的函数或变量编译失败 / 运行时崩溃
SVL-2类型漂移参数数量或类型与实际签名不匹配类型错误 / 逻辑错误
SVL-3数据流污染使用未初始化变量、创建循环引用或引入死代码NameError / 内存泄漏
SVL-4协议违规违反业务步骤的必要顺序——在认证用户前就签发 JWT安全漏洞 / 业务逻辑错误

这些错误并非源于推理失败，而是源于模型缺乏对程序真相的确定性访问。

1.2 现有缓解策略的局限性

  • 事后校验（linter、测试套件、人工审查）：在错误生成后检测，无法从源头预防
  • 检索增强生成（RAG）：将项目上下文注入 prompt，降低但不消除幻觉——模型仍然是正确性的唯一仲裁者
  • 迭代提示工程：通过精心设计的指令引导模型行为，但无法提供合规性的形式化保证

这三种策略都将 LLM 置于系统中心，试图从外部修正其输出。它们缺乏第一性原理的约束机制。

1.3 核心命题

AI 生成的代码在进入代码库之前，必须先通过一个免疫层——可验证、具备记忆能力、能识别并防御反复出现的错误模式。这一免疫层包含三种相互依赖的能力：

  • 天然免疫：基于模式快速拒绝符号、类型和数据流违规（SVL-1/2/3）——系统内置的防御
  • 获得性免疫：从 Failure Corpus 学习，生成特异性的防御规则（抗体），主动预防未来同类错误
  • 免疫记忆：将成功和失败模式沉淀为持久知识，系统随使用持续进化，越用越可靠

3.2 Strategy Planner —— 策略规划层

这是 v3 研究和实验最密集的层。Strategy Planner 解决的问题是：给定自然语言意图和 500+ 个函数，如何选出正确的 3-5 个函数并连成可执行的调用链？整个过程零 LLM 调用——纯图搜索。

3.2.1 算法流程

intent → extractKeywords → scoreNode (6维评分) → 种子选择

3.4 Semantic State Graph (SSG) —— 获得性免疫层

SSG 建模系统资源的有效状态及其允许的转移。以认证协议为例：

UNAUTHENTICATED → AUTHENTICATED → TOKEN_ISSUED → SESSION_ACTIVE

每个函数声明 pre_states、post_states 和可选的 invalidate 规则。SSG 验证器在处理动作树时模拟状态转移，拒绝任何前置状态与当前活跃状态无交集的调用——即使所有其他 SVL 级别均通过。这将验证从静态正确性提升为行为合法性。

v3 增强：Invariant 三层验证

Invariant检查内容性能
Invariant-0statesBefore 必须等于从头重建的状态全量审计 3ms
Invariant-1statesAfter 必须等于 applyDelta(statesBefore, acquired, invalidated)
Invariant-2 (v3 新增)每个 acquired 必须在 post_states 中；每个 invalidated 必须在 invalidate 中；拒绝重复 acquire 已存在状态

增量验证: 0.05ms/步。快速模式: PROGMUNE_FAST_VALIDATE=true 跳过 validateTransition 中的 I-1（由 checkLedgerConsistency 覆盖）。

4.2 关键洞察

Graph 的正确位置是 LLM 的下游，不是替代 LLM。

Graph 基于字符串匹配——dispatch.includes("send") 永远是 false。LLM 天然知道 "send receipt" → dispatch + issueBill。两者的正确分工：

LLM 跨语义鸿沟选种子 → Graph 做数据流路由连成链

4.3 渐进策略：按需付费的智能路由

Step 1: 关键词评分 → needsLLM=false? → Graph 路由 → 完成 (90% 场景, 0 额外 LLM)
                                          ↓ needsLLM=true
Step 2: LLM 语义选种子 → 注入 Graph → 路由 → 完成 (10% 场景, +1 LLM)
经济性：Step 2 只在语义鸿沟时触发。正常任务走关键词+Graph（0 额外成本），语义鸿沟任务走 LLM 种子桥接（+1 次调用）。needsLLM 标志由 strategy-planner 的 selectCapabilityChains() 返回——种子数 ≤2 且图 >50 节点时自动标记。

十、结论

Progmune Runtime v3 证明了：通过颠倒 LLM 与程序真相之间的关系——将 IR 确立为第一性原理，并使 LLM 成为受约束的启发式提议器——我们可以实现具有强语义保证的可验证代码合成。

三个确定事实：

  1. Graph 减少搜索空间 50-61%——在所有规模上确定性地缩小候选函数集，不依赖 LLM 随机性。
  2. LLM + Graph 联合架构达到 90% 精度——LLM 跨语义鸿沟选种子，Graph 做数据流路由连成链，触及手动天花板。
  3. Pipeline 完整闭环——意图→Graph→Planner→Validator→Emitter→Compile 全链路打通，Auto-Repair 处理编译失败。

一个未解决问题：

在所有规模的 Graph ON/OFF 实验中，Graph 从未赢过。原因已定位——入口处的关键词评分锁死了 Graph 的天花板。LLM 种子注入是已验证的突破口（132 函数: 48%→90%），但尚未在 519 函数的真实场景中打破平局。

v3 的唯一验收标准：

在一个 200+ 函数的真实外部代码库上，LLM+Graph 联合架构的首次通过率显著高于纯 LLM。只要这一条成立，知识层就从"有趣的设计"变成了"有证据的能力"。
